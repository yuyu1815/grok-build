# サンドボックスモード

サンドボックスモードは、OS レベルのカーネルプリミティブ（Linux では Landlock、macOS では Seatbelt）を使用して、エージェントプロセスとそこから起動されたコマンドがファイルシステムおよびネットワーク上でアクセスできる範囲を制限します。カーネルはプロセスの存続中、これらの制限を適用します。

サンドボックスモードはデフォルトで無効です。

---

## クイックスタート

```bash
# ワークスペースサンドボックスで実行（すべて読み取り可、CWD + 一時ディレクトリ + ~/.grok/ へ書き込み可）
grok --sandbox workspace

# 読み取り専用モード（すべて読み取り可、~/.grok/ + 一時ディレクトリのみ書き込み可）
grok --sandbox read-only

# 最も制限の厳しいプロファイル（CWD + システムパスを読み取り可、CWD + 一時ディレクトリ + ~/.grok/ へ書き込み可、子プロセスのネットワーク接続なし）
grok --sandbox strict
```

## 組み込みプロファイル

| プロファイル | FS 読み取り | FS 書き込み | 子プロセスのネットワーク | 用途 |
| ------------ | ----------- | ----------- | -------------------------- | ---- |
| `off`（デフォルト） | 無制限 | 無制限 | 無制限 | サンドボックスなし |
| `workspace` | すべて | CWD + `~/.grok/` + `/tmp` + `/var/tmp` | 許可 | 通常の開発 |
| `devbox` | すべて | `/data` を除くすべてのトップレベルディレクトリ | 許可 | 使い捨ての開発 VM |
| `read-only` | すべて | `~/.grok/` + `/tmp` + `/var/tmp` | ブロック¹ | 調査、コードレビュー |
| `strict` | CWD + システムパス | CWD + `~/.grok/` + `/tmp` + `/var/tmp` | ブロック¹ | 信頼できないコード |

¹ 子プロセスのネットワークブロックが適用されるのは **Linux のみ**です（seccomp を使用）。macOS では何も行われず、これらのプロファイルは子プロセスのネットワークを制限しません。

プロファイルに加えて特定のファイル（例: `.env` や認証情報のパス）をブロックするには、`deny` リストを持つ[カスタムプロファイル](#custom-profiles)を定義します。この制限はカーネルによって適用され（読み取り + 書き込み/名前変更）、`**/*.pem` のような glob パターンにも対応します。

### プロファイルの詳細

**workspace** -- 日常的な開発に推奨されるプロファイルです。エージェントは依存関係やシステムライブラリなどを把握するため、システム上のすべてのファイルを読み取れますが、書き込み先は現在の作業ディレクトリ、`~/.grok/`、一時ディレクトリ（`/tmp`、`/var/tmp`、および macOS の一時ディレクトリ）に限られます。`web_search` や MCP サーバーなどのツールによるネットワークアクセスは許可されます。

**devbox** -- 使い捨ての開発 VM 用に予約された組み込みプロファイルです。エージェントはすべての場所を読み取れ、`/data` と仮想ファイルシステム（`/proc`、`/sys`、`/dev`）を除くすべてのトップレベルディレクトリ（ホームディレクトリを含む）へ書き込めます。ネットワークアクセスは許可されます。`--sandbox devbox` は組み込みプロファイルを実行し、`sandbox.toml` で定義した `[profiles.devbox]` より優先されます。

**read-only** -- プロジェクトファイルを変更せずにエージェントにコードを分析させたい場合に使用します。エージェントはすべてを読み取れますが、書き込み先はセッションの永続化に必要な `~/.grok/` と一時ディレクトリに限られます。子プロセスのネットワークアクセスは Linux ではブロックされます（macOS では何も行われません）。

**strict** -- 信頼できないコードをレビューするための、最も制限の厳しいプロファイルです。エージェントが読み取れるのは、現在の作業ディレクトリ内のファイルと必須のシステムパスだけです。書き込み先は CWD、`~/.grok/`、一時ディレクトリに限られます。子プロセスのネットワークアクセスは Linux ではブロックされます（macOS では何も行われません）。

## カスタムプロファイル

カスタムサンドボックスプロファイルは、`~/.grok/sandbox.toml`（グローバル）または `.grok/sandbox.toml`（プロジェクト単位）に作成します。

```toml
[profiles.project]
# 組み込みプロファイルを基にして、設定を上書き
extends = "workspace"
restrict_network = true

# エージェントが読み取れるが、書き込み/削除はできないパス
read_only = ["/data"]

# 追加の読み書き可能なパス
read_write = ["/tmp/scratch"]

# カーネルで拒否するパスまたは glob（読み取り + 書き込み/名前変更、強制適用。以下の注記を参照）
deny = ["/data/shared-secrets", "**/.env", "**/*.pem"]
```

カスタムプロファイルを使用するには、次を実行します。

```bash
grok --sandbox project
```

カスタムプロファイルには組み込みプロファイルと同じ名前を使用できません。`--sandbox devbox` は常に組み込みの `devbox` プロファイルを実行し、定義した `[profiles.devbox]` より優先されます。

グローバルファイルとプロジェクト単位のファイルで同じ名前のカスタムプロファイルを定義した場合、ユーザーレベルの定義が優先され、プロジェクト側の定義は無視されます。2 つの定義が異なる場合、Grok は起動時に競合を警告します。TUI ではウェルカム画面に、ヘッドレス実行では stderr に表示されます。同一内容の重複定義では警告されません。

### カスタムプロファイルのフィールド

| フィールド | 型 | 説明 |
| ---------- | -- | ---- |
| `extends` | String | 継承元の組み込み基本プロファイル（`workspace`、`devbox`、`read-only`、`strict`）。省略時のデフォルトは `workspace` |
| `restrict_network` | Boolean | 子プロセスのネットワークアクセスをブロックする |
| `read_only` | String[] | 追加の読み取り専用パス |
| `read_write` | String[] | 追加の読み書き可能なパス |
| `deny` | String[] | カーネルで拒否するパスまたは glob（読み取り + 書き込み/名前変更。注記を参照）。`*`、`?`、`[` のいずれかを含むエントリは glob |

> **`deny` に関する注記:** 空でない `deny` リストは、**カーネルによって適用**されます。拒否されたパスは、macOS では Seatbelt、Linux では bwrap の bind-over によって**読み取りと書き込み/名前変更が拒否**されるため、拒否されたパスを（`bash`、`grep`、サブエージェントから）読み取ることも、拒否対象外へ移動して読み取ることもできません（`mv secret x && cat x` による回避策は塞がれています）。**Linux** で読み取りを拒否するには `bubblewrap` が必要です。`bubblewrap` がない場合（または拒否するパスを 1 つでもバインドできない場合）、Grok は拒否対象のパスを公開したまま実行せず、起動を拒否します（`/data` の書き込みだけを拒否する `devbox` は、引き続き Landlock にフォールバックします）。`deny` に含まれないパスへの書き込みは、`read_write` で付与した権限によって制御されます。

> **`deny` 内の glob:** エントリに `*`、`?`、`[` のいずれかが含まれる場合、そのエントリは **glob** です。これらの文字は**常に** glob を意味します。名前にこれらの文字を含むリテラルファイルを拒否するには、代わりに親ディレクトリを指定してください。サポートされる gitignore 形式のサブセットは次のとおりです。
>
> - `*` — 1 つのパスセグメント内の任意の文字列（`/` で止まる）
> - `?` — セグメント内の任意の 1 文字
> - `**` — ディレクトリをまたぐ（パスセグメント全体として使用。例: `**/`、`a/**`）。`**/` は 0 個のディレクトリにも一致するため、`**/.env` は `.env` と `sub/.env` の両方に一致する
> - `[abc]` / `[a-z]` — 文字クラス。先頭の `!` **または** `^` は否定を表す（`[!a]` と `[^a]` はどちらも「`a` 以外」を意味する）
>
> 波括弧による選択肢（`{a,b}`）、バックスラッシュエスケープ、特殊な文字クラス形式の `[]…]`（先頭のリテラル `]`）、POSIX の `[[:…:]]` は**サポートされません**。そのため、2 つのプラットフォームで glob の解釈が異なることはありません。サポートされていないメタ文字を使った glob や、不正な形式の glob がある場合、Grok は**両方**のプラットフォームで**起動を拒否**します（フェイルクローズ）。`*.{pem,key}` ではなく、`*.pem` と `*.key` を別々のエントリとして記述してください。
>
> 相対 glob はワークスペースを基準に、絶対 glob（例: `/home/**/.ssh`）はそのリテラルプレフィックスを基準にします。glob ではないエントリは、完全一致のパス照合を維持します。それ以外の適用方法はプラットフォームによって異なります。
>
> - **macOS は完全に保護されます:** 各 glob は実行時に適用される Seatbelt の正規表現になるため、Grok の起動後に作成されたファイルでも、一致すれば拒否されます。
> - **Linux はベストエフォートです:** マウント名前空間では実行時に glob を処理できないため、各 glob は**起動時に存在する**ファイルへ展開され、それらに bind-over が適用されます。**後から**作成され、glob に一致するファイルは対象になりません。Linux で確実な保護が必要なものには、正確なパスを指定してください。一致するファイルが多すぎる glob や、走査するツリーが深すぎる、または広すぎる glob がある場合、Grok は適用不足のまま実行せず、**起動を拒否**します。

## 仕組み

サンドボックスは、コマンドごとのラッピングではなく、起動時にカーネルプリミティブを使用して **grok プロセス全体**へ適用されます。つまり、すべてのツール操作が対象になります。

- `read_file`、`search_replace`、`list_dir` -- プロセス内で Landlock/Seatbelt による制限を受ける
- `bash` コマンド、`grep`（rg）-- 子プロセスが FS 制限を自動的に継承する
- ネットワーク -- Linux では seccomp により子プロセスをブロックできる。macOS では何も行われない

サンドボックスは適用後に**解除できません**。エージェントが実行時に制限を緩和することはできません。

## セッションの再開

セッションの開始時に使用したプロファイルはセッションとともに保存され、**そのセッションの存続中は固定**されます。セッションを再開すると（`grok --resume <id>`、`grok --continue`、または `grok -r`）、Grok は同じプロファイルを自動的に復元します。そのため、`--sandbox workspace` で開始したセッションが知らないうちにより厳格なデフォルトで再開され、以前は動作していたコマンドが失敗することはありません。

再開してもセッションのサンドボックスは**変更されません**。

- 再開時に `--sandbox` を省略すると、セッションに保存されたプロファイルが使用されます。
- 保存済みのプロファイルと**一致する** `--sandbox <profile>` は指定できます。
- 保存済みのプロファイルと**異なる** `--sandbox <profile>` を指定すると、**エラーで拒否されます**。再開したセッションのサンドボックス変更は安全上の落とし穴です（制限する意図だったセッションのアクセス範囲を広げたり、より広いアクセス権に依存していたセッションを壊したりする可能性があります）。別のプロファイルを使用するには、新しいセッションを開始してください。

**新しい**セッションのプロファイルは、次の優先順位で解決されます。

1. 明示的な `--sandbox <profile>` フラグまたは `GROK_SANDBOX` 環境変数
2. 設定内の `[sandbox] profile`
3. `off`（サンドボックスなし）

## 対応プラットフォーム

| プラットフォーム | 仕組み | 最小バージョン |
| ---------------- | ------ | -------------- |
| Linux | Landlock | カーネル 5.13 以降 |
| macOS | Seatbelt | macOS（全バージョン） |

サンドボックスを適用できない場合（例: 未対応のカーネル、必要な entitlement がない場合）、Grok は警告をログに記録し、制限を適用せずに続行します。ただし、明示的に要求された**カスタムプロファイル**は例外です。**macOS と Linux の両方**で、カスタムプロファイルを適用できない場合（不明なプロファイル、不正な `sandbox.toml`、または Linux で空でない `deny` に必要な `bubblewrap` が利用できない場合）、Grok は拒否対象のパスを公開したまま実行せず、起動を拒否します。

## ネットワーク制限

Linux では、`restrict_network` を設定したプロファイルは、seccomp を介して**子プロセス**（bash コマンド、スクリプト）のネットワークアクセスをブロックします。macOS ではネットワークブロックは何も行いません。プロセス内で HTTP リクエストを行う組み込みツール（Web 検索、LLM API 呼び出し）は影響を受けません。エージェントが機能するにはネットワークアクセスが必要です。

実際には、Linux では次のようになります。

- `web_search`、`web_fetch`、LLM API は常にネットワークへアクセスできる
- `restrict_network` が有効な場合、`curl`、`wget`、`npm install` などの `bash` コマンドはブロックされる

---

## イベントログ

デバッグ用に、サンドボックスイベントが `~/.grok/sandbox-events.jsonl` に記録されます。イベントには次の情報が含まれます。

- 適用されたプロファイル（プロファイル名、タイムスタンプ）
- 違反（拒否されたパスへのアクセス試行）

## サンドボックスモードを使用する場面

**`workspace` を使用する場合:**

- 自分のプロジェクトで作業しており、基本的な書き込み保護が必要な場合
- 共有環境で実行しており、変更範囲を制限したい場合

**`deny` リストを持つカスタムプロファイルを定義する場合:**

- 基本プロファイルに加えて、特定のファイル（例: `.env` や認証情報のパス）をブロックする必要がある場合
- `read_file` ツールだけでなく、`bash`、`grep`、サブエージェントにも及ぶカーネルレベルの制限が必要な場合

**`read-only` を使用する場合:**

- 信頼できないコードをレビューする場合
- 誤って変更するリスクを避けてコードベースを調査する場合
- コード分析や監査を実行する場合

**`strict` を使用する場合:**

- 信頼できないコードやサードパーティ製コードを分析する場合
- セキュリティ上重要な環境で実行する場合
- 最大限の分離が必要な場合

**サンドボックスを使用しない場合:**

- エージェントが依存関係をインストールする必要がある場合（`npm install`、`pip install`）
- エージェントが作業ディレクトリ外のファイルを変更する必要がある場合
- 信頼できる環境で作業しており、最大限の柔軟性が必要な場合

## トレードオフ

| 観点 | サンドボックスなし | サンドボックスあり |
| ---- | ------------------ | ------------------ |
| 安全性 | エージェントがシステム全体へアクセスできる | エージェントはプロファイルの規則に制限される |
| 機能 | あらゆる操作が可能 | プロファイルによる制限あり |
| パフォーマンス | オーバーヘッドなし | 無視できる程度のオーバーヘッド |
| 復旧 | エージェントを信頼する必要がある | カーネルが境界を適用する |

サンドボックスは、独立した VM ではなく、OS レベルの Landlock、Linux のマウント名前空間、macOS の Seatbelt を通じて制限を適用します。
