<a id="plan-mode"></a>

# プランモード

プランモードは、構造化された計画フェーズです。エージェントはコードを書く前にコードベースを調査し、実装方針を設計します。適切な方針が明確でなく、実装前にユーザーの意見を確認することで大幅な手戻りを防げるタスクに使用してください。

---

<a id="what-plan-mode-does"></a>

## プランモードの動作

プランモードが有効な場合、エージェントは次の処理を行います。

1. コードベースを読み取り、検索して、既存のパターンとアーキテクチャを把握する
2. 実装方針を設計し、プランファイルに書き込む
3. 必要に応じて `ask_user_question` を使用し、具体的な疑問点を明確にする
4. `exit_plan_mode` を呼び出し、承認を得るためにプランを提示する

プランモードでは、プランファイル以外は読み取り専用です。プランファイル（セッションディレクトリ内の `plan.md`）の編集は自動承認されますが、その他のファイルの編集はすべて即座に拒否されます。ツール呼び出しは失敗し、編集可能なパスがプランファイルだけであることを示す短いメッセージが表示されます。この制限は、常時承認を含むすべての権限モードで適用されます。計画と実装を分離することで、コードが書かれる前に方針を確認し、修正できます。

---

<a id="how-to-enter-plan-mode"></a>

## プランモードへの移行方法

<a id="agent-initiated-entry"></a>

### エージェントによる移行

タスクの方針に実質的な曖昧さがあると判断した場合、エージェントはプランモードに移行します。エージェントが `enter_plan_mode` ツールを呼び出すと、プランモードが有効になる前にユーザーの承認が必要です。拒否した場合、エージェントは通常モードのままになります。

**プランモードが適している例:**

- 「アプリにユーザー認証を追加して」-- 選択肢が多く、方針が明確でない（セッションか JWT か、トークンの保存方法、ミドルウェアの構成）
- 「データパイプラインを再設計して」-- 方針を誤ると多大な手戻りが生じる大規模な再構成
- 「API にキャッシュを追加して」-- 妥当な方針が複数ある（Redis、インメモリ、ファイルベース）
- 「リアルタイム更新を追加して」-- アーキテクチャ上の判断が必要（WebSockets、SSE、ポーリング）

**プランモードが適していない例:**

- 「ユーザープロフィールに削除ボタンを追加して」-- 実装方法が明確
- 「README の誤字を修正して」-- 単純な作業
- 「API のエラー処理を更新して」-- まず作業を始め、必要に応じて具体的に質問すればよい
- 「検索機能に取りかかれる？」-- ユーザーは計画ではなく、作業の開始を求めている

<a id="user-initiated-entry"></a>

### ユーザーによる移行

次の 2 通りの方法で、ユーザー自身がプランモードに移行できます。

- **`/plan`** -- プランモードに移行します。次のプロンプトを送信すると、プランモードが有効になります。`/plan <description>` を実行すると、プランモードへの移行と、その説明を指定したターンの開始を一度に行えます。
- **Shift+Tab** -- セッションモードを、通常、プラン、常時承認、通常の順に切り替えます。通常モードでは、1 回押すとプランモードになります。

プランの作成後は、**`/view-plan`**（エイリアス: `/show-plan`、`/plan-view`）を実行すると、保存されたプレビューを再度開けます。

---

<a id="the-plan-file"></a>

## プランファイル

プランは、セッションディレクトリ内の `plan.md`（`~/.grok/sessions/<cwd>/<session-id>/plan.md`）に書き込まれます。`<cwd>` はリテラルパスではなく、エンコードされたディレクトリ名です。

プランファイルには次の内容が含まれます。

- 変更する理由を説明する **Context** セクション
- すべての代替案ではなく、推奨する方針
- 変更する重要なファイルのパス
- 再利用する既存の関数やユーティリティと、そのファイルパス
- 変更をエンドツーエンドでテストする方法を説明する検証セクション

---

<a id="plan-approval"></a>

## プランの承認

計画が完了すると、エージェントは `exit_plan_mode` ツールを呼び出します。このツールがディスクからプランファイルを読み取ると、TUI にプランのスクロール可能なプレビューが開き、下部にアクションバーが表示されます。

エージェントがプランを書かずに終了した場合（`plan.md` が空または存在しない場合）も、同じ承認画面が開き、空であることを示す明確なメッセージが表示されます。ここでは、承認して実装を開始する、変更を依頼してエージェントを計画に戻す、または終了することができます。最小表示モードでは、空である旨の通知がスクロールバックに記録され、コントロール欄の見出しに **No plan written yet** と表示されます。

<a id="reviewing-the-plan"></a>

### プランの確認

矢印キーまたは `j`/`k` でプランをスクロールします。アクションバーには次のショートカットが表示されます。

| ショートカット | 操作 |
| -------------- | ---- |
| `a` | プランを承認して実装を開始します。保留中のコメントがある場合は `approve w/ comments` と表示され、承認とともにコメントが送信されます。 |
| `s` | 変更を依頼します。フォーカスがプロンプトに移るため、修正内容を入力し、`Enter` を押して送信します。 |
| `c` | 選択した行または行範囲にコメントします。 |
| `q` | プランを終了します。承認せずにプランを破棄し、プランモードを無効にします。 |

`Tab` を押すと、プランのプレビューとプロンプトの間でフォーカスが移動します。

<a id="providing-feedback"></a>

### フィードバックの送信

承認画面には、次の 3 つのフォーカス状態があります。

- **プレビュー**: プランをスクロールし、コメントする行を選択します。
- **コメント入力**: 選択した行範囲にインラインコメントを追加します（`c` を押すか、行上で `Enter` を押します）。
- **プロンプト**: 自由形式の修正内容を入力します。

`Tab` を押すと、プレビューとプロンプトの間で切り替わります。インラインコメント、自由形式のメモ、またはその両方をフィードバックとして送信すると、エージェントが受け取ってプランを修正します。反復して調整できるよう、プランモードは有効なまま維持されます。

<a id="leaving-the-approval-view"></a>

### 承認画面を閉じる

`Esc` を押すと、フォーカスがプロンプトからプランのプレビューに戻ります。承認もフィードバックの送信もせずに承認画面を閉じるには、`q` を押してプランを終了します。終了すると、提示されたプランが破棄され、プランモードが無効になります。

<a id="plan-mode-lifecycle"></a>

## プランモードのライフサイクル

プランモードのステートマシンには、次の 4 つの状態があります。

| 状態 | 説明 |
| ---- | ---- |
| `Inactive` | 通常の動作モード。プランモードの制約はありません。 |
| `Pending` | クライアントがプランモードを ON に切り替えたものの、まだプロンプトが送信されていない状態です。 |
| `Active` | プランモードが有効な状態です。プランファイルの編集は自動承認され、その他のファイルの編集は拒否されます。 |
| `ExitPending` | ターンの実行中に、ユーザーがプランモードを OFF に切り替えた状態です。 |

状態遷移:

```
Inactive    --> Active   (enter_plan_mode tool called and approved -- skips Pending)
Inactive    --> Pending  (you toggle plan mode on with /plan or Shift+Tab)
Pending     --> Active   (your first prompt activates plan mode)
Active      --> Inactive (exit_plan_mode approved, or you toggle plan mode off when idle)
Active      --> ExitPending (you toggle plan mode off while a turn is in-flight)
ExitPending --> Inactive (after the turn completes)
```

プランモードの状態はディスクに永続化され、プロセスを再起動しても維持されます。一時的な状態（`Pending`、`ExitPending`）は進行中のやり取りに依存するため、再起動時には `Inactive` にまとめられます。

---

<a id="edits-during-plan-mode"></a>

## プランモード中の編集

プランモードが有効な間、プランファイルの編集は確認なしで自動承認されるため、エージェントは自由にプランを修正できます。**その他のすべてのファイルの編集は実行前に拒否されます**。エージェントには、編集可能なパスがプランファイルだけであることを示す短いメッセージが表示されます。

この制限は権限モードに左右されません。

- **常時承認（yolo）は、プランモードの背後で有効なまま維持されます。** 編集以外のツール（bash コマンド、読み取り、MCP ツール）は引き続き自動実行されますが、プランモードの終了を承認するまでファイル編集はブロックされます。プランが承認されると、実装時には常時承認が再開されます。
- Bash コマンドによるファイル書き込みは検査されません。プランモードがブロックするのは編集ツールであり、シェルのリダイレクトではありません。
- サブエージェントには、親セッションのプランモードによる編集制限が適用されません。各サブエージェントは新しいプランモードトラッカー（`Inactive`）で開始するため、親がプランモードのままでも、`general-purpose`（またはその他の書き込み可能な）サブエージェントはファイルを編集できます。また、親の権限モード（常時承認を含む）を継承します。`explore` などの読み取り専用タイプには、引き続き固有のツールセットによる制限が適用されます。

プランモードが有効な間、ステータスフラグには `plan` と表示されます。その背後で常時承認が有効な場合、プランモードを終了すると常時承認のフラグが再表示されます。

---

<a id="plan-mode-and-compaction"></a>

## プランモードと圧縮

プランモードが有効なセッション中に `/compact` を実行しても、プランモードの状態は維持されます。圧縮後のコンテキストにはプランモードが有効であることを示すリマインダーが含まれるため、エージェントは圧縮後も計画を続けます。

---

<a id="when-plan-mode-is-appropriate"></a>

## プランモードが適している場合

**プランモードを使用する場合:**

- アーキテクチャに大きな曖昧さがあるタスク（妥当な方針が複数ある場合）
- 実装前に調査が必要な、不明確な要件
- 方針を誤ると多大な手戻りが生じる、影響の大きな再構成

**プランモードを使用しない場合:**

- 実装方法が明確なタスク
- バグを理解すれば修正方法が明らかなバグ修正
- 既存の規則に従って機能を追加する場合
- 単純な変更（名前変更、書式調整、テスト追加）
- 調査や探索のタスク（代わりにサブエージェントを使用）
